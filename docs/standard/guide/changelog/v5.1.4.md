# v5.1.4 更新日志

> 发布日期：2026-10-28 · 标准版

> 本文档记录 v5.1.4 的完整变更。跨版本升级前请先阅读[升级指南](./upgrade.md)。

本版本主线为一次完整的前后端联调收束：定位并修复「后端启动目录漂移 → 跨库 Token 互认 → 会员接口 401 → 会员菜单不可见」的连锁问题，并将暴露的健壮性缺陷（异常分级、半登录态、JWT 密钥缺省）一并固化；同期并入前台站点配置体系、会员中心重构、全站搜索等功能批次，并完成后台通用 CRUD 组件的刷新条件保留与弹窗布局修复。

### 🔧 会员信息接口异常分级与日志（MemberController::getProfile）

`/api/member/user-info` 的异常处理由「一切异常统一返回 401」改为分级返回，并补充错误日志：

- **401（凭证失效）**：仅 `UnauthorizedHttpException`（无 Authorization 头 / Token 无效）保持原语义
- **500（服务异常）**：数据库、缓存、事件监听等非鉴权异常统一记入 `Logger::error`（含 `file:line` 定位），返回「获取会员信息失败，请稍后重试」
- **影响范围**：前台会员中心及消费该接口的联调链路。此前服务端故障（如连库失败）会被伪装成「用户凭证失效」，导致前端反复触发 Token 刷新且日志无迹可循
- **迁移指引**：前端如对 401 有「自动登出」逻辑无需调整；如需区分提示，可对 500 显示通用错误而非跳转登录

### 🔧 会员菜单初始化数据统一登录可见（web.php）

`resource/data/menu/web.php` 中「积分记录 / 余额记录 / 每日签到」3 条会员菜单的 `is_no_auth` 由 `0` 修正为 `1`：

- **背景**：前台菜单可见性为三层判定（`is_public` → 登录态 → `is_no_auth` → 权限码）。会员菜单此前携带 `web:member:*` 权限码且 `is_no_auth=0`，而新注册会员天然不持有任何权限码，形成「菜单要权限码、会员永远没有权限码」的死锁，登录成功后右上角会员菜单仍被过滤
- **影响范围**：新安装环境会员菜单随登录直接可见（共 8 条会员菜单语义统一：登录即可见）；按权限码管控的场景不受影响——可将 `md_web_menu.is_no_auth` 改回 `0` 并为会员标签挂载权限码
- **迁移指引**：存量数据库需执行 SQL 对齐（见[升级提示](#升级提示)）

### 🔧 会员资料保存后清理列表缓存

- 修复会员资料保存后列表缓存未失效的问题（`19c670b`）

### 🔧 端口恢复开源默认 8500

- 进程监听、第三方回调、push hook 的后端端口统一恢复开源默认 `8500`（`d101c3e`）

### 📦 配置与依赖对齐

- 对齐私有基线配置，插件包目录移出版本库（`41f5828`）
- 重新生成权限清单与依赖锁文件，对齐站点配置权限码（`995e788`）
- `.example.env` 新增 JWT 配置段：`JWT_SECRET` / `JWT_ALGO` / `JWT_ACCESS_TTL` / `JWT_REFRESH_TTL` / `JWT_LOGIN_MODE`（`92bb079`）
  - **风险背景**：`JWT_SECRET` 未配置时框架回退内置开发密钥，多环境（如指向不同数据库的部署副本）互相认签 Token——刷新接口不查库即可为失效会话签发新 Token，是本次「refresh 成功但 user-info 仍 401」怪象的成因之一
  - **迁移指引**：所有环境（含开发）在 `.env` 显式配置 `JWT_SECRET`（`openssl rand -hex 32`）；配置后全部已登录会话失效，请安排低峰期

### 🔧 登录后用户信息拉取失败强制登出（消除半登录态）

`stores/member.ts` 的 `setToken()` 在用户信息拉取后增加兜底判定：

- **行为变更**：`getMemberInfoSilent()` 完成后若 `info` 仍为空（接口 4xx/5xx 或返回空数据），立即 `logout('/')` 清空 Token 并抛出「获取用户信息失败，请重新登录」；同时 `components/login-dialog/register.vue` 对 `setToken` 补齐 `await`，保证异常正确进入注册流程的 catch
- **影响范围**：账密/验证码登录、注册、第三方登录回调、Token 自动刷新（`request.ts` → `refreshToken()` → `setToken`）全链路生效。此前存在「Token 有效但 `info=null`」的半登录态：刷新接口看似成功，但依赖 `memberStore.info` 的导航菜单、权限判断全部失效
- **迁移指引**：登录/注册组件如自行调用 `setToken`，请确认位于 `try/catch` 内且使用 `await`；第三方登录链路请预期可能收到「获取用户信息失败」提示并引导重新登录

### 🔧 通用 CRUD 工具栏刷新保留当前搜索条件

后台列表页工具栏刷新按钮此前重新查询时不携带搜索条件（请求参数中甚至混入 `isTrusted` 等事件属性）：

- **根因**：vxe-table 工具栏刷新按钮会把原生事件对象（PointerEvent）透传给 `proxyConfig.ajax.query`；而通用 CRUD 组件（`crud.vue`）对 grid options 的响应式绑定使框架层的查询参数包装（`extendProxyOptions`）失效，事件对象被直接展开进请求，搜索条件全部丢失
- **修复**（`crud.vue`、`core/plugins/vxe-table/extends.ts`、`use-vxe-grid.vue`）：刷新触发时改读**当前搜索表单值**（含已修改但未点「搜索」提交的条件）参与查询，并回写为「最新提交值」——刷新后的翻页、排序、增删改局部刷新均沿用相同条件，表单显示与数据始终一致；刷新改走 `refreshSoft` 路径，树形展开状态一并保持
- **影响范围**：所有基于通用 CRUD（`useCrud`）的列表页（系统菜单、职位、部门、会员用户等）
- **行为变更**：刷新由「重放上次提交条件并回到第 1 页」调整为「应用当前表单条件并保持当前页与展开状态」；「搜索」「重置」「翻页」「排序」「初始加载」行为不变

### 🔧 弹窗布局与滚动条修复（dialog.vue）

新增/编辑 Modal 弹窗此前表单被挤在左半边、滚动条出现在弹窗中部、右侧大片留白：

- **根因**：宽度类被同时传给弹窗外壳与 vben Modal 的内部滚动容器（`:content-class="dialogWidth"`），滚动容器被限宽为弹窗的一半——滚动条出现在容器右缘（即弹窗中部）而非弹窗边缘
- **修复**：移除传给滚动容器的宽度类，滚动容器恢复占满弹窗宽度，**滚动条恒定贴弹窗最右缘**；表单内容默认对半（`w-1/2`）紧凑显示，并新增 `FormDialogOptions.formWidth` 配置项——滚动条位置与表单列数布局（单列/双列/多列）完全解耦，已实测单列 Modal、双列 Modal、双列 Drawer（拖大备注文本框触发滚动）场景一致
- **迁移指引**：现有业务无需调整（默认对半显示）；如需表单占满弹窗，在 `formDialog` 配置 `formWidth: 'w-full'`
- 顺手修复 `dialog.vue` 遗留的 lint 报错（联合类型排序）

### 🔧 修复与工程对齐

## 迁移与联调路径说明

本版本经历了「迁移期镜像 → 源代码开放」的联调路径切换，过程与现状如下：

- **迁移期（已完成）**：仓库根稳定路径 `madong/backend/` 曾为源目录 `madong/source/backend` 的镜像，用于推送前的联调过渡。镜像 `.env` 与源目录指向不同数据库且代码存在滞后，从镜像启动曾引发 `/api/site/site-config` 等新接口 404 与会员接口 401 连锁问题；过渡期约定任何代码改动一律落在源目录提交，禁止在镜像内开发
- **现状（源代码开放方式，已生效）**：本批变更推送完成后，`madong/backend/`、`madong/template/web/`、`madong/template/admin/` 三个稳定路径仓库已拉取最新代码（同一 commit），**后续统一以稳定路径为工作目录**——开发、启动、联调一律在稳定路径进行
- **迁移期源目录已移除**：`madong/source/*`（backend / web / admin）已删除，仅存在于历史记录中，不再有任何文档或流程引用
- **遗留风险提示**：启动后端前仍须确认进程工作目录为稳定路径 `madong/backend`（本次排障中「refresh 成功但 user-info 仍 401」即由误用镜像启动导致）

## 注意事项

- **进程管理**：Windows 下后端启动脚本 `windows.php` 为看门狗进程（监控文件变化并整树重建子进程）。停止后端必须 `taskkill /F /T /PID <windows.php 的 PID>`；仅杀单个 worker 会被联动重建或留下半死状态
- **端口约定**：后端 Webman `8500`、前台 Nuxt `3000`、后台 Vite `5500`、安装向导 `8500/install`
- **JWT 密钥变更**：配置 `JWT_SECRET` 后所有已签发 Token 与 Redis 中的会话索引不再互认，全量用户需重新登录

## 升级提示

1. **代码**：backend / web / admin / manual 各仓库 `git pull`
2. **数据库**（存量环境）：`UPDATE md_web_menu SET is_no_auth = 1 WHERE category = '2' AND app = 'web';`（8 行，会员菜单对齐新初始化数据）；新装环境无需处理（初始化数据已修正）
3. **配置**：`.env` 配置 `JWT_SECRET`（`openssl rand -hex 32`），并同步更新部署清单/密钥管理
4. **重启**：重启 Webman 进程（源目录 `php windows.php` 或 Supervisor），使接口异常分级生效；前台/后台如以构建产物部署需重新 `pnpm build`
5. **验证**：
   - 登录前台 → 右上角出现会员菜单（账户设置下个人资料/用户设置/修改密码/第三方绑定/积分/余额/签到 8 项）
   - `GET /api/member/user-info` 携带 Token 返回 `code=0`
   - 服务端异常（如断开数据库）时接口返回 500 且日志出现 `member/user-info 失败` 记录，不再返回 401
